# Rio：网页与移动端体验提案

状态：产品设计方向，待 review；尚未实现 UI 或验证帧率。

## 1. 核心体验

打开 Rio 后，用户进入一个安静、轻盈的对话空间：选择要聊的 Agent，点一下开始说话。已有默认 Agent 时，不先进入配置向导。只有尚未绑定任何 Agent 时，才显示一个明确的连接入口。

语音和文字属于同一个会话。语音过程中可展开文字记录、复制结果或用键盘补充；技术连接参数只出现在设置和诊断中。

## 2. 视觉方向：流动的水面

Rio 的中心视觉是一片有深度的、缓慢变化的水面。暖白背景、深墨文字、克制的青绿与琥珀色，用留白、精细字体和连续运动形成识别，不依赖堆叠卡片或大量发光效果。

| 元素 | 设计 |
| --- | --- |
| 页面背景 | 暖白 `#F6F4EF`，极轻的颗粒/柔光；夜间版本用深墨底降低屏幕亮度 |
| 文字 | 近黑 `#172A2B`，大字号短句；系统中文字体和清晰的数字排版 |
| 输入声音 | 青绿涟漪，由真实麦克风音量驱动 |
| 输出声音 | 暖琥珀色流线，由实际播放音量驱动 |
| 工具任务 | 中心视觉下方一行简短状态，例如“正在查看日历”；需要时展开详情 |
| 连接异常 | 收束动画并显示明确文案与重连操作，不用无尽旋转掩盖失败 |

颜色只是初始方向，实施时按真实背景检查文本和控件对比度。Agent 个性通过名字、头像/单字标记和少量色彩表达，不把复杂品牌系统作为 POC 前置条件。

## 3. 主对话页

从上到下只有四个主要区域：

1. 顶部：当前 Agent 的小型切换入口、连接状态和设置按钮。
2. 中部：声音可视化。待机时低幅度呼吸；交谈时显示输入和输出两种独立运动。
3. 下方：最近说出的一两句话，可展开完整对话和任务结果。记录自动跟随只发生在用户已位于底部时。
4. 底部：开始/结束、静音和键盘入口。移动端主操作位于拇指容易触达的位置。

**全双工不是“聆听/思考/说话”三选一。** 页面独立呈现麦克风、播放和任务三个状态：可以一边显示“正在查询”，一边播放语音，同时仍接收用户声音。不能用一个“说话中”状态把麦克风动画和输入能力关掉。

停止任务和结束语音有各自清楚的行为：结束语音会释放麦克风和关闭收费会话；后台任务若继续运行，页面明确显示，不暗示它已经取消。静音保留连接，界面不会把它表现为结束。

## 4. Agent 选择

点击顶部 Agent 名称出现紧凑选择层，只显示名称、机器标签和最近连接状态。default/cherry 是初始绑定例子，不把它们写死在产品代码中。

切换时保留旧会话可返回，建立新会话归属。正在进行的语音需要先结束，避免把旧 Agent 的上下文或晚到回复带给新 Agent。只有一个 Agent 时仍保留其名称，简化选择入口。

## 5. 沉浸式设置

设置从当前对话空间平滑展开，保留空间位置感。桌面是宽阔的聚焦面板，手机是适应安全区的全屏层；打开和返回均不重载应用，也不丢失未发送文字。

设置分为三个清楚的入口，每次聚焦一个任务：

| 入口 | 用户可做什么 |
| --- | --- |
| Agents | 添加/编辑独立 Gateway，命名，配置 hostname 和两层凭据，查看最后验证时间 |
| Voice | 设置 provider URL、key、voice 和时长/预算；单独启动语音测试 |
| Connection guide | 按步骤完成本机 API Server、Tunnel 和 Access；查看当前失败在哪一层 |

连接向导采用渐进步骤：选择机器/profile → 按说明准备本机 API → 创建命名 Tunnel 与 Access → 填入凭据 → 测试真实连接。步骤内提供可复制模板，凭据输入隐藏且保存后不可回读完整值。

不在 UI 中索要 Cloudflare 管理 token。Tunnel 创建说明链接至当下官方文档；Rio 保存访问该 Gateway 所需的最小运行凭据。

诊断结果区分：配置已保存、Access 验证通过、Gateway 可达、所需能力齐备、真实任务验证通过。不能把一个绿色 HTTP 200 当成所有层均已连接。

打开设置不会自动开启麦克风或创建 Live session；在通话中打开时保留明显的麦克风/结束入口。修改 provider 或 Agent 的新配置用于下一次会话，避免中途改凭据造成难以解释的断线。

## 6. 动画与响应性能

- 页面层间过渡以 220–320 ms 的 transform/opacity 为初始范围，随实际触控体验调整；不阻塞按钮反馈。
- 声音视觉优先用 Canvas 2D 或 SVG/CSS，直接订阅音量数据；不把每帧数据推入整个 React 树。
- 输入与输出各有平滑包络，噪声门避免空调声导致持续强动画。连接成功、收到首字、任务完成以轻微而明确的变化反馈。
- 文本流按小批次刷新，保持选中文字、滚动位置和屏幕阅读顺序。
- 桌面目标流畅 60 fps；移动端按电量/负载降级。后台停止纯视觉循环，网络和音频生命周期独立管理；这些是设计目标，须在实机验收。
- `prefers-reduced-motion` 下保留静态状态和低幅度反馈，不依赖运动传达重要信息。

## 7. 移动端与可访问性验收

| 场景 | 设计要求 |
| --- | --- |
| 单手使用 | 主要点击目标至少 44 px，底栏避开 home indicator，不能依靠 hover |
| 软键盘弹出 | 使用动态视口和安全区，输入框与结束按钮不被遮挡 |
| 麦克风/播放权限 | 用户手势开启；权限失败有明确解释和重试；处理 iOS autoplay 与 AudioContext 恢复 |
| 蓝牙/扬声器 | 验证回声消除、耳机切换和设备断开；默认浏览器语音处理能力优先 |
| 锁屏/切后台 | 不承诺后台持续通话；检测媒体状态，及时提示暂停/结束，服务端兜底费用上限 |
| 网络切换 | 页面保留最后确认的任务结果；显示重连状态，禁止自动重复执行原任务 |
| 键盘和读屏 | 完整焦点路径；设置层正确管理焦点并可退出；新语音片段不逐字轰炸 aria-live |
| 授权动作 | 单次确认卡说明具体动作；允许拒绝，不用语音推测代替清楚的确认 |

## 8. 实施顺序

文本 POC 先实现可读的对话、Agent 归属、进度与错误，用真实事件检验交互状态。随后建立中心声音视觉和沉浸式设置，再接语音。最后在真实手机上调整动画、触控和长任务体验。

评审关注点是：日常页面是否足够轻、全双工状态是否真实、设置是否让连接过程清楚、移动端是否始终能停止和返回。视觉完成度在实现后用实机页面与录屏验证，本轮不把设计提案标为成品。
